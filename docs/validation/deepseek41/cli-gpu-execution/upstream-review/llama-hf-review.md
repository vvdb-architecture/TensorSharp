## TensorSharp candidate ordering and causal constraints

**First candidate: one bounded pool job for both already-known Engram tables.** Current hash output is `[layer][token][hash column]`; both tables' hashes are available before their read loop. Interleave table index first within each row index so 48 decode reads can fill the same 16-worker pool without two separate barriers. All table/row bounds must be validated before any read. Capture table pointers, byte strides, output pointers, dimensions, and the dequantizer by value: retaining the old `lookup` callback after that function returns would leave references to an expired stack frame. Outputs stay separate; image rows become zero before table access; upload only after all jobs drain. No changes to hashing, token history, quantization, or GPU graph mathematics are necessary.

Two full output buffers would use `2 * nt * 24 * 256 * sizeof(float)`: 48 KiB at one token, 12 MiB at 256, and 48 MiB at 1024, twice the old reusable buffer. Bound additional staging by grouping tables for large configurations; a single existing table larger than the cap should run alone. Test byte parity and read order across 1/3/256-token batches, group boundaries, image rows, invalid later-table hashes before any work, worker failure/drain, and interleaved slot numerical/reset cases. The claimed four-to-three read-wave reduction is a homogeneous-blocked-read model, not a guaranteed filesystem or end-to-end gain.

**Known-prompt prefetch is causally possible, but larger in scope.** Future prompt token IDs are already known. Prefetch must hash using a private history snapshot, including negative image barriers, without committing history, positions, or logits early. Future generated tokens are unknown until sampling, so ordinary next-token decode cannot be prefetched this way. Cancellation, reset, slot destruction, and buffer reuse must join/cancel or safely retire outstanding reads. The current synchronous V4.1 graph path does not provide this pipeline for free.

**A bounded dequantized row cache needs hit-rate evidence first.** Immutable per-model table rows permit a key containing table identity and row ID, with exact existing dequantization output retained. This could avoid cold rereads after OS eviction or repeated dequantization, but it duplicates the OS cache and expands quantized rows to F32. Measure per-table repeated-row frequency and working-set size on actual traces before choosing a default capacity or asserting a benefit. No hit-rate evidence was collected in this read-only review.

**Async uploads or layer-14 overlap require explicit lifetimes and dependencies.** Merely replacing `ggml_backend_tensor_set` with an async variant while reusing/freeing its host buffer is unsafe. Use pinned persistent staging, per-device completion events, and a graph dependency before the relevant Engram consumer; wait before reuse/free/reset. Starting layer 14's input-independent lookup while earlier layers compute is a real scheduling option, but splitting or gating the graph is a separate candidate from joining the host lookup job.

The existing nt1/nt3 parallel-row fix directly addresses the observed serial host input preparation. Source research provides mechanisms and constraints; it does not establish an unmeasured speedup or eliminate the need for the actual VM comparison.
