A TP callback-only CPU graph plans **one active ggml thread**, even when the persistent fallback pool contains 32 threads. `executor::build` requests `ggml_map_custom3(..., n_tasks=1)` in [ggml_ops_deepseek41_tp.cpp](../../../TensorSharp.GGML.Native/ggml_ops_deepseek41_tp.cpp). `ggml_get_n_tasks` honors that request, and `ggml_graph_plan` sets the plan thread count to the maximum task count across that split, capped by the configured count ([ggml-cpu.c](../../../ExternalProjects/ggml/src/ggml-cpu/ggml-cpu.c), lines2465–2473 and3054–3055). Scheduler input transfers happen outside the split's compute graph, so they do not themselves add multithreaded copy nodes to its CPU plan ([ggml-backend.cpp](../../../ExternalProjects/ggml/src/ggml-backend.cpp), lines1460 and1669–1792).

Pool capacity still has overhead. In the pthread implementation, kickoff broadcasts to the existing workers regardless of the plan's active count. Workers whose IDs exceed that count skip computation; barriers return immediately when the active count is 1. Those inactive workers can still wake and pass through the hybrid polling/wait loop. Default polling is 50. This establishes a possible 32-versus-1 wake/poll cost, not its measured importance or a 32-thread barrier inside the TP callback (`ggml-cpu.c`, lines576–581,3180–3243 and3280–3310; [ggml.c](../../../ExternalProjects/ggml/src/ggml.c), line8121).

CPU-MoE layers differ: `build_moe_host` explicitly pins routed gate/up/down, SwiGLU, weighting and reduction nodes to CPU. Their matrix, activation and elementwise tasks request the configured CPU thread count. The shared gate/up/down projections now remain on the layer GPU. Thus reducing the fallback count to 1 would also reduce actual host-expert parallelism in an offload profile ([ggml_ops_deepseek4.cpp](../../../TensorSharp.GGML.Native/ggml_ops_deepseek4.cpp), lines3690–3720 and3832–3850; `ggml-cpu.c`, lines2253–2267 and2329–2361).

The remaining TP host work includes scheduler GPU-to-host input transfer, eight independent rank submissions and synchronizations, rank-output downloads, a single-threaded fixed-order host reduction, and transfer of the reduced output back to the layer GPU. Its rank worker count is independent of the fallback pool count. Engram lookups use a separate I/O pool; hash/mask construction also occurs outside the ggml CPU plan. Lowering fallback threads does not parallelize or remove these operations.

This is source-only analysis of the final 6b3 implementation. The pin regression tests observed shared-projection ownership on a five-layer fixture, not every node of the full-checkpoint graph. Other CPU-assigned nodes such as a materializing `CONT`, or a shape-specific unsupported GPU operation, could raise a split's maximum task count; no full-model assignment dump was taken in this review. A post-pin full-model threads 1 result remains **unmeasured**. There is no evidence here that 1 is optimal, and no broad new thread sweep is warranted ahead of the scheduled final layer, smoke18 and existing-model checks.
