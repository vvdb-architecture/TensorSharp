The Windows V4.1 TP weight reader now owns the opened `FILE` with local RAII until seek, length and bounds validation succeed. Previously, throwing from the constructor left its file open because the reader destructor could not run. A failed seek is now checked explicitly. The exact Windows-only change is in [windows-reader.patch](windows-reader.patch); Linux code and the native ABI are unchanged.

The [portable harness](../../../../eng/tests/dsv41-windows-reader.py) extracts the actual production Windows constructor branch, compiles it with POSIX seek/tell adapters, and observes real file descriptors. The [old source control](before.json) passes 2/6 checks and leaks a file on truncated input, offset past end, failed seek and failed length query. The [fixed source](after.json) passes all 6/6 checks, including successful construction and failed open. This is an extracted-control test on macOS, not Windows execution.

The complete old and new translation units preprocess identically on local macOS, with SHA-256 `43c36c698bd0cb48f315d6f41f02b5fcc02e912cb7f438a5e3755e2723757e84`; [commands and results](posix-preprocess.json) preserve that check. The VM incremental rebuild also produced a byte-identical Linux library: `cmp` exit 0, SHA-256 `6b3b5ab3c333c59423bc10efe9f18b5f0483fd0a478823647471c5de7e736014`, 204,523,264 bytes. The [identity report](native-windows-reader-identity.json) and [build log](native-windows-reader-build.log) preserve that result. Running/private server libraries and archived controls were untouched. [The manifest](manifest.json) records exact source, harness and artifact hashes.
